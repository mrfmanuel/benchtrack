# BenchTrack — Product Specification

> Source of truth for scope and behavior. If a request conflicts with this file, flag it instead of silently deviating. Update it when scope intentionally changes.

## 1. Problem

Small independent computer-repair shops (one technician, a bench, a WhatsApp number) track repairs in notebooks, chat threads and memory. This causes three recurring problems:

1. **Lost context** — the technician forgets what was diagnosed, which parts were ordered, or what price was quoted.
2. **Constant "is it ready yet?" messages** — customers have no way to check status, so they call or message repeatedly.
3. **No overview** — it is hard to see at a glance which devices are waiting for parts, which are ready for pickup, and which have been sitting on the bench for too long.

## 2. Solution

**BenchTrack** is a lightweight web app for a single repair shop:

- **Staff area** (protected): register customers and repair tickets, move tickets through a fixed status workflow, add notes, and see a dashboard of open work.
- **Public tracking page** (no login): a customer enters the tracking code printed on their receipt and sees the current status and a timeline — without exposing personal data.

## 3. Users

| User | Access | Goal |
|------|--------|------|
| Technician / shop owner (staff) | Staff token | Manage customers and tickets, update status |
| Customer | Tracking code only | Check repair status without contacting the shop |

## 4. Core features (v1)

### F1 — Customers
- Create, list, search (by name or phone), view and edit a customer.
- Fields: `name` (required), `phone` (required), `email` (optional), `created_at`.

### F2 — Repair tickets
- Create a ticket for an existing customer.
- Fields: `device_type` (laptop, desktop, phone, tablet, printer, other), `brand`, `model`, `serial_number` (optional), `reported_issue` (required), `diagnosis` (optional), `estimated_cost` (optional, decimal, ≥ 0), `status`, `tracking_code` (generated), `created_at`, `updated_at`.
- `tracking_code` is generated by the backend, unique, short and unambiguous (e.g. `BT-7K3QX`, no `0/O/1/I`).
- List tickets with filters by status and free-text search (tracking code, customer name, brand/model).
- Edit ticket details (not the tracking code).

### F3 — Status workflow and timeline
- Statuses: `received → diagnosing → waiting_parts → repairing → ready → delivered`, plus `cancelled`.
- Allowed transitions are enforced by the backend:
  - `received → diagnosing | cancelled`
  - `diagnosing → waiting_parts | repairing | ready | cancelled`
  - `waiting_parts → repairing | cancelled`
  - `repairing → waiting_parts | ready | cancelled`
  - `ready → delivered | repairing`
  - `delivered`, `cancelled` are final.
- Ticket creation records an initial event (`from_status = null`, `to_status = received`).
- Every status change creates a **status event** (`from_status`, `to_status`, optional `note`, `created_at`). Invalid transitions return `409 Conflict`.
- Staff can add free-text notes to the timeline without changing status.

### F4 — Public tracking
- `GET /api/public/track/{tracking_code}` returns: tracking code, device type, brand/model, current status, last update time, and the status timeline (status + timestamp only — **no notes, no customer name/phone/email, no cost**).
- Unknown code → `404`. The public endpoint is rate-limited to reduce code guessing.

### F5 — Dashboard
- Counts of tickets per status.
- List of "stale" tickets: open (not `delivered`/`cancelled`) and not updated for more than 7 days.

## 5. Authentication (deliberately simple)

- Single shop, single staff role. All `/api/*` endpoints except `/api/health` and `/api/public/*` require `Authorization: Bearer <STAFF_TOKEN>`.
- `STAFF_TOKEN` is provided via environment variable, never committed. The frontend asks for it once and keeps it in `localStorage`; a "Sign out" button clears it.

## 6. Non-functional requirements

- Responsive UI (desktop first, usable on mobile — the technician often checks on the phone).
- All UI copy in English.
- Database-agnostic persistence via SQLAlchemy: SQLite for local dev/tests, PostgreSQL in Docker Compose and production. Configured via `DATABASE_URL`.
- Health endpoint `GET /api/health` for container and platform health checks.
- Structured (JSON) logs in production.
- Seed script with **fictional** demo data only.

## 7. Out of scope (v1)

Multiple shops, multiple staff accounts/roles, invoicing and payments, inventory/parts stock, SMS/WhatsApp/email notifications, file/photo uploads, real-time updates (websockets), i18n.

## 8. Acceptance scenarios

1. Staff creates customer "Ana Mora" and a laptop ticket → ticket has status `received` and a tracking code.
2. Staff moves the ticket `received → diagnosing → waiting_parts → repairing → ready → delivered` → timeline shows 6 entries in order.
3. Staff tries `received → ready` → API returns `409`, UI shows a clear error.
4. Customer opens the tracking page, enters the code → sees status and timeline, but not the customer's phone or internal notes.
5. Request to a staff endpoint without a token → `401`.
6. Dashboard shows correct counts per status and lists a ticket untouched for 8 days as stale.

## 9. Clarifications and decisions (v1)

Answers to the open questions raised during spec review. Where this section is more specific than sections 1–8, this section wins.

### Data model and validation
1. **Phone** — required, normalized on save (spaces, dashes and parentheses removed); must match `^\+?\d{8,15}$`. **Unique** per customer → duplicate returns `409`.
2. **Ticket fields** — `device_type`, `brand`, `reported_issue` required; `model`, `serial_number`, `diagnosis`, `estimated_cost` optional.
3. **estimated_cost** — `Numeric(10,2)`, currency **CRC** (Costa Rican colón, shown as `₡`), range `0–10,000,000`. Editable until the ticket is final (`delivered`/`cancelled`).
4. **Max lengths** — name 100, phone 20, email 254, brand/model/serial 60, reported_issue 2000, diagnosis 2000, note 1000. Violations → `422`.
5. **Reassignment** — not allowed; `customer_id` is immutable after creation.
6. **Deleting** — no deletes in v1 (customers or tickets). A ticket is closed with status `cancelled`.
7. **Final tickets** — `delivered`/`cancelled` tickets are read-only (details and status → `409`), but **notes can still be added** (e.g. warranty follow-up).

### Status workflow and timeline
8. **Event model** — one `ticket_events` table with `kind` = `status` | `note`. Status events have `from_status`/`to_status` (+ optional note text); note events have both statuses `null` and required `note`. The public endpoint only returns `kind = status`, and never the note text.
9. **Same-status change** — `409` (not a valid transition).
10. **updated_at** — bumped by any change (details edit, status change, note). Stale detection uses `updated_at`.
11. **Public "last update"** — timestamp of the **last status event**, not `updated_at`.

### Tracking codes
12. **Format** — `BT-` + 5 characters from `23456789ABCDEFGHJKMNPQRSTVWXYZ` (excludes 0, O, 1, I, L, U). Generated with `secrets`; unique DB constraint; retry up to 5 times on collision, then fail with `500`.
13. **Lookup** — case-insensitive, surrounding whitespace trimmed, `BT-` prefix optional (`7k3qx` → `BT-7K3QX`).

### Public endpoint and security
14. **Rate limit** — `GET /api/public/track/*`: 10 requests per minute per client IP, in-memory sliding window. Over the limit → `429` with `Retry-After` header and the standard error body. Known limitation: in-memory works for a single instance only (v1 runs one replica); documented in `docs/`. Client IP comes from `X-Forwarded-For` only when running behind the platform proxy (uvicorn `--proxy-headers`).
15. **Public response whitelist** — exactly: `tracking_code`, `device_type`, `brand`, `model`, `status`, `last_status_change_at`, `timeline: [{status, at}]`. Explicitly excluded: customer data, `serial_number`, `diagnosis`, `estimated_cost`, notes, internal IDs.
16. **Logging** — tracking codes are masked in access/application logs (`BT-*****`).
17. **Auth errors** — missing **or** wrong token → `401` (single role, so no `403`).
18. **STAFF_TOKEN** — the app refuses to start if it is unset or shorter than 16 characters.

### API shape
19. **Error format** — every error uses `{"error": {"code": "<snake_case>", "message": "<human readable>", "details": <optional>}}` (e.g. `invalid_transition`, `not_found`, `unauthorized`, `validation_error`, `rate_limited`, `conflict`).
20. **Lists** — `limit` (default 50, max 200) + `offset`; response `{ "items": [...], "total": n }`. Tickets sorted by `created_at` desc; customers by `name` asc. Search `q` = case-insensitive substring match.
21. **Dashboard** — counts for **all 7 statuses**; stale = open ticket with `updated_at` older than 7 × 24 h (strictly greater). All timestamps stored and returned in **UTC** (ISO 8601 with `Z`); the UI shows browser local time.
22. **Health** — `GET /api/health` → `200 {"status": "ok", "database": "ok"}`; if the DB check (`SELECT 1`) fails → `503 {"status": "degraded", "database": "error"}`.

### UI and operations
23. **Public routes** — `/track` (form) and `/track/:code` (pre-filled, auto-lookup). QR codes are out of scope for v1.
24. **Receipt** — in scope, minimal: a "Print receipt" view from the ticket detail (print CSS + `window.print()`) with shop name, date, customer name, device, reported issue, tracking code and the tracking URL.
25. **Bad saved token** — any `401` clears the stored token and returns to the sign-in screen with "Invalid or expired token".
26. **Migrations** — Alembic. Containers run `alembic upgrade head` on startup; unit tests may use `create_all` on SQLite; integration tests run migrations on PostgreSQL.
27. **Logging config** — `LOG_LEVEL` (default `INFO`) and `LOG_FORMAT` = `text` | `json` (default `text`; `json` in Compose and production).
